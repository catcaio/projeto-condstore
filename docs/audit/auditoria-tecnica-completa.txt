  1. MULTI-TENANT / SEGURANÇA
================================================================================

ARQUITETURA GERAL
-----------------
O sistema implementa isolamento multi-tenant via "tenantId" derivado da sessão
JWT em todos os handlers protegidos. O guard "requireAdmin" (src/infra/auth/
guards.ts) valida o token, normaliza tenantId e sub (rejeita strings vazias),
verifica a role, e retorna um GuardedSession tipado com tenantId garantido.
Rotas internas usam "requireInternalToken" com token de serviço separado —
correto para workers, CI/CD e exportações.

PROBLEMA ENCONTRADO E CORRIGIDO — Vetor de enumeração de tenants
-----------------------------------------------------------------
Arquivo  : src/app/api/cockpit/metrics/frank/route.ts

Status   : CORRIGIDO nesta auditoria.

  2. FRANK / MODO SUPERVISIONADO
================================================================================

VISÃO GERAL DO SISTEMA FRANK
-----------------------------
Frank é o assistente de IA integrado ao WhatsApp. Opera em três modos:
  SUPERVISED  — Frank prepara dados, operador humano envia.
  ASSISTED    — Frank responde automaticamente em queries informacionais simples.
  AUTONOMOUS  — Frank responde sozinho fora do horário comercial (off-hours).

A lógica de controle fica em src/modules/frank/conversation-control.ts.

SALVAGUARDAS IMPLEMENTADAS — TODAS FUNCIONANDO
-----------------------------------------------

1. INTENTS SENSÍVEIS SEMPRE SUPERVISIONADOS
   Arquivo : src/modules/frank/conversation-control.ts
   Intents : CONFIRM_QUOTE, CONFIRM_ORDER, PAYMENT, REQUEST_INVOICE,
             REQUEST_BOLETO, COMPLAINT, PRICE_NEGOTIATION, FRETE, PRODUTO
   Regra   : Qualquer mensagem detectada nessas categorias → modo SUPERVISED
             independente de confiança, horário ou disponibilidade de operador.

2. LIMIAR DE CONFIANÇA
   ASSISTED_MIN_CONFIDENCE  = 0.6  (mínimo para modo assistido)
   AUTONOMOUS_MIN_CONFIDENCE = 0.8  (mínimo para modo autônomo)
   SUPERVISED_MAX_CONFIDENCE = 0.6  (abaixo disso → sempre supervisionado)

3. HORÁRIO COMERCIAL
   Horário : 08:00–18:00 BRT (segunda a sexta)
   Regra   : Durante horário comercial, Frank nunca entra em modo AUTONOMOUS
             mesmo se operador não está online — usa SUPERVISED ou ASSISTED.

4. LIMITE DE RESPOSTAS AUTÔNOMAS
   Constante : MAX_AUTO_RESPONSES = 5
   Regra     : Após 5 respostas autônomas consecutivas → força handoff para
               operador humano independentemente de outros fatores.

5. DETECÇÃO DE FRUSTRAÇÃO
   Palavras-chave (14+):
     "não foi isso", "nao foi isso", "não entendi", "já falei",
     "você não respondeu", "não é isso", "falar com alguém",
     "falar com atendente" (e variações sem acentos)
   Regra : Qualquer match → modo SUPERVISED forçado imediatamente.

6. OPERADOR ONLINE
   Regra : Se operatorOnline = true → NEVER AUTONOMOUS. Frank usa SUPERVISED
           ou ASSISTED baseado na confiança e tipo de intent.

7. KILL SWITCH GLOBAL
   Variável de ambiente: FRANK_RUNTIME_MODE=SUPERVISED_ONLY
   Efeito : Bloqueia toda autonomia de Frank globalmente, sem deploy.

SANITIZAÇÃO DE PII NOS PAYLOADS LLM
-------------------------------------
Arquivo : src/core/ai/frank-event-sanitize.ts (260 linhas)
Funcionalidade:
  - Remove números de telefone (E.164 + formatos BR com/sem pontuação)
  - Remove endereços de e-mail (regex case-insensitive)
  - Remove API keys (padrão sk-xxx)
  - Remove URLs de banco de dados (mysql://, https:// em metadata)
  - Remove chaves de metadata PII (userId, phoneNumber, email, from, to)
  - Preserva hashes seguros (phoneHash, sessionId, correlationId)
  - Trunca textos em 2000 caracteres por mensagem
  - Limita histórico a 12 mensagens

PROBLEMA ENCONTRADO E CORRIGIDO — Tipagem any nos payloads de eventos
----------------------------------------------------------------------
Arquivo  : src/modules/frank/intents/intent.events.ts
           src/modules/frank/suggestions/suggestion.events.ts
Problema : Parâmetros "payload: any" nas funções exportadas permitiam que
           qualquer chamador passasse campos arbitrários, incluindo PII como
           messageText, phone, suggestedResponse, etc. O frank-event-sanitize
           só age no layer LLM, não nos eventos operacionais.
Risco    : MÉDIO — regressão futura poderia vazar PII no event bus sem
           warning do compilador.
Correção : Substituídos por interfaces tipadas explícitas:
           IntentCapturedPayload   : { intentId, sessionId, conversationId?,
                                       messageId?, detectedIntent?, confidence? }
           IntentValidatedPayload  : { intentId, validatedBy }
           IntentIgnoredPayload    : { intentId, ignoredBy }
           SuggestionGeneratedPayload : { suggestionId, sessionId,
                                          conversationId, intent, confidence }
           SuggestionApprovedPayload  : { suggestionId, sessionId, approvedBy,
                                          edited: boolean }
           SuggestionRejectedPayload  : { suggestionId, sessionId, rejectedBy }
           Todas estendem Record<string, unknown> para compatibilidade com bus.
Status   : CORRIGIDO nesta auditoria. TypeScript valida, 101 testes passam.

================================================================================

FLUXO COMPLETO
--------------
Captura → Validate → Link-Playbook (ou) Create-Playbook → Emit Event

1. Captura : IntentTrainingService.captureIntent() persiste em frank_intent_training
             com status='captured'. Evento intent_captured emitido.

2. Validação: IntentTrainingService.validateIntent() atualiza para 'validated'.
              Evento intent_validated emitido. Operador confirma ou ignora.

3. Linker  : intent-linker.service.ts oferece duas rotas:
             a) linkToExistingPlaybook — associa intent a playbook existente
                via playbookId, atualiza linkStatus.
             b) convertToNewPlaybook   — cria novo playbook a partir do intent,
                retorna playbookId novo.

4. Persistência: intent-linker.repository.ts salva playbookId e linkStatus
                 com filtro tenantId em todas as operações.

PROBLEMA CORRIGIDO — Total count errado no endpoint de auditoria
-----------------------------------------------------------------
Arquivo  : src/app/api/cockpit/audit/route.ts
Problema : O campo "total" no response de paginação era calculado como:
             total = COUNT(tenantEvents) + domineFails.length + privacyLogs.length
           Os arrays domineFails e privacyLogs eram buscados com .limit(limit),
           então em páginas > 1 (offset > 0) retornavam menos itens do que o

           navegação às páginas finais.
Correção : Adicionados COUNT(*) via SQL para domineEvents e userConsentsLog.
           Adicionado offset nas queries cross-domain para paginação correta:
             db.select({ count: sql<number>'count(*)' })
               .from(domineEvents).where(domineConditions)
           Todas as três tabelas agora têm COUNT e offset corretos.
Status   : CORRIGIDO nesta auditoria.
